# Teacher Review → Parent Summary Contract\n\nStatus: design contract only. No production schema, scheduler, provider, or AI Production Core changes are included.\n\n## Purpose\nDefine a safe persistence/state contract for periodic student summaries that are prepared for teacher review before any parent communication is sent.\n\n## Boundary\nThe feature is separate from Class / Student Insights and from the existing Parent Messages delivery surface.\nFlow: Insights → Summary Draft → Authoritative Student/Parent Validation → Teacher Review → Approval → Delivery → Delivery Result → Audit\nAI may prepare content, but it must never infer or choose the recipient.\n\n## Canonical draft identity\nA summary draft represents exactly one school, student, period kind (weekly or monthly), period start/end, authoritative parent recipient reference, reviewing teacher, and generated content/version.\nRecommended immutable identity: school_id + student_id + period_type + period_start + period_end.\nOnly one active draft/version may be approved for a given identity.\n\n## State machine\ndraft → pending_review → approved → queued → sending → sent\nTerminal/non-send states: rejected, cancelled, failed.\nOnly pending_review can be approved or rejected.\nOnly the assigned/re-authorized class teacher can approve/reject.\nApproval must revalidate student school/class authority and the authoritative parent relationship.\napproved is not delivery success.\nsent means the provider accepted the message according to the provider contract; provider acceptance must not be represented as delivery unless the provider supplies delivery confirmation.\nFailed delivery must retain the approved content and error/result for retry/audit.\nA rejected/cancelled draft must never enter the send queue.\n\n## Recipient contract\nRecipient data is resolved from the authoritative students relationship at draft/approval time.\nThe client must not supply an arbitrary parent identifier as authority.\nMinimum validation: student exists and is active; student.school_id matches session school; student class is within teacher authority; parent contact/channel is present and valid for the selected provider; recipient belongs to that student relationship; approval happens before delivery.\nIf any check fails, fail closed.\n\n## Teacher authority\nThe reviewing teacher must have active class authority for the student's actual class.\nDo not trust a client-provided class name as authority.\nUse the existing school/session/teacher boundary model enforced by web_has_permission and class assignments.\n\n## Content/versioning\nA draft should preserve generated summary, source snapshot/reference metadata, generation timestamp, generator type/version, reviewer edits if supported, approved content snapshot, approval timestamp and teacher, and rejection reason if rejected.\nAfter approval, the approved content becomes immutable for that send attempt.\nAny substantive edit after approval must create a new version and return the draft to pending_review.\n\n## Idempotency/audit\nEvery approval and delivery attempt needs correlation_id, idempotency_key, school_id, student_id, draft/version id, actor, action, result/status, and error/provider response metadata where applicable.\nApproval must be exactly-once at the state-transition level.\nDelivery must be idempotent so retries cannot create duplicate parent messages.\n\n## Existing-system integration\nExisting capabilities that can be reused: students.parent_name / parent_tg_id / parent_phone / parent_phone2 / parent_email; teacher_class_assignments; parent_comms; rpc_send_parent_comm(); audit_log; session validation and web_has_permission.\nImportant limitation: rpc_send_parent_comm() currently queues a parent_comms row and does not itself prove provider delivery. Therefore it must not be treated as the final delivery-confirmation contract for this feature.\n\n## Required persistence before implementation\nA dedicated summary-draft/review persistence model is required. Do not overload parent_comms with approval workflow state.\nThe model should support draft identity and period, authoritative student/parent linkage, reviewer assignment, content/version, review state, approval/rejection metadata, delivery state, correlation/idempotency, provider result/error, and timestamps.\n\n## Explicit non-goals\nThis checkpoint does not add a new AI action to the 117-action registry; activate AI Production Core; auto-send messages; infer recipients; create a scheduler; select a messaging provider; claim provider delivery; or modify existing production RPCs.\n\n## Gate for next implementation step\nBefore applying a production migration, verify the exact parent-channel/provider contract and choose the smallest dedicated schema/API surface that can enforce the state machine above. Then implement backend authorization and persistence first, followed by teacher-review UI, then delivery integration.\nProduction Core remains locked until the complete business capability is independently verified.
